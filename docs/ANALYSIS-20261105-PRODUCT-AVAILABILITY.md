# 商品下架、归档与列表标记：只读验证

日期：2026-11-05。用户要求先分析是否能定期标记订单列表、罗盘列表中的下架和归档商品。本轮未开发、部署或修改生产配置/数据；只读取现有商品标识并调用商品信息查询接口。

## 已验证结论

可通过现有店铺API凭证区分售卖状态、归档状态；用户提供的下架样本还实际返回了两条具体原因。无需以消费者网页是否跳转作为主要判断依据。

本次现网请求均为只读查询，虽然Seller API使用POST方法，并未调用归档、上下架、库存或价格修改接口。原始脱敏字段快照保留在仓库外 `K:\github\diagnostics\product-status-analysis`，密钥未输出、未保存到本地结果或Git。

## 真实样本

店铺：Luo007；查询 `/v3/product/info/list`。

| 字段 | 用户给出的SKU 6161843658 | 正常对照SKU 6161845451 |
| --- | --- | --- |
| is_archived / is_autoarchived | false / false | false / false |
| statuses.status | price_sent | price_sent |
| statuses.moderate_status | approved | approved |
| statuses.status_name | Не продается（不出售） | Продается（销售中） |
| statuses.status_description | Убран из продажи（已从销售中移除） | 空 |
| availabilities中对应SKU的availability | HIDDEN | AVAILABLE |
| 对应reasons | id=6：Нарушение авторских прав（侵犯版权）；id=81：Отсутствуют документы на бренд（缺少品牌文件） | 空 |
| errors | 空 | 空 |
| 库存 | 1021 | 1022 |

原因的完整字段路径是 `availabilities[].reasons[].human_text.text`，并有数值id。最初仅查看statuses/errors未发现原因；补充检查完整响应键名后，定位到availabilities，实际与用户后台截图的两条原因一致。不能把空errors视为无下架原因。

另以 `/v3/product/list` 的offer_id过滤查询 `ALL` 和 `IN_SALE`：ALL返回以上两个商品，IN_SALE仅返回正常对照商品，形成独立交叉验证。不可把“不在IN_SALE”直接等同于投诉下架，因为缺库存等情况也可能不在售。

额外抽查 `visibility=ARCHIVED` 的1个真实归档商品，详情返回 `is_archived=true`、`is_autoarchived=false`、`availabilities=[]`。该样本未创建成功（sku=0），留有旧建卡审核错误，不能把那些errors当作“归档原因”。归档标记不附会下架原因，也不能承诺所有归档商品的其他错误字段都为空。

## 展示和判断建议（未实施）

- 列表只加两类异常标记：红色“已下架”、灰色“已归档”；正常商品保持简洁。订单列表、罗盘列表及详情共用同一快照，按店铺、商品ID及SKU正确关联，不能跨店套用状态。
- 归档优先按实际归档字段处理；非归档商品结合整体售卖状态及对应SKU/source的availabilities判断。多source冲突、未知状态、查询无结果不硬判为下架。
- 下架标记的悬停或详情展示API真实原因及最后成功检查时间；归档只显示归档状态和检查时间。未知原因可显示平台原文，不把库存、审核通过或任何错误单独当成投诉依据。
- 两页面展示同一状态数据；建议服务器每30分钟批量更新，并可有手动刷新入口。请求限速、按商品去重，不在每次列表加载或鼠标悬停时实时调用Ozon。
- 复用现有商品轮询的ALL/IN_SALE读取能力，但现有products_snapshot只保存首次出现和上新事件，尚未持久化当前售卖状态、下架原因或供页面读取的快照，不能说当前已具备此功能。
- 网络错误保留上次成功状态并提示过期；完整分页失败不能用缺失项推断商品下架。首次运行先建立当前状态，后续另存首次发现变化时间和恢复时间。
- 本次下架样本的statuses.status_updated_at仍为2026-10-27，与用户最近发现下架的时间不一致；该字段不能直接展示成“实际下架时间”，应区分平台给出的时间与我们首次检测时间。
- 保留历史订单和利润口径。这里只读监测，不自动归档、不恢复上架、不改商品链接、价格或采购成本。

## 网页链接检查的边界

网页跳转、403/验证码、地区限制、缺货和卡片合并都不能单独认定为投诉下架。若将来确需监测跳转，应独立标记“链接异常待核实”，不得覆盖Seller API的售卖状态。用户当前需求通过官方商品API即可先覆盖提供的真实问题样本。

官方接口入口：[Seller API](https://docs.ozon.ru/api/seller/)。本次字段及原因的结论来自当前店铺真实接口响应，不依赖第三方博客对枚举的猜测。
